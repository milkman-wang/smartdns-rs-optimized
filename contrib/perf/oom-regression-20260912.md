# Passwall 内存修复后的 BE10000 性能对照

比较提交 `ef064b4` 与修复前已发布的 `0.13.1-24` 无界面核心。前者增加规则共享、减少域名副本，并把 IPSet 更新移到 DNS 回复之前；本次没有覆盖安装生产服务。

完整名单的启动 RSS 下降 86.5%–87.2%，名单匹配吞吐基本持平或略高；带 IPSet 的双核冷/热吞吐分别提高 4.7% / 6.0%。可见的代价是普通小配置单核热缓存吞吐下降 1.8%（三轮范围不重叠），以及 IPSet 场景在 1000 QPS 下的中位延迟增加 36–41 μs。该延迟成本对应回复前等待内核写入确认；本次使用单个 A 地址回复，多地址或多个集合的成本还需相应测量。

## 方法与边界

- BE10000 / Cortex-A73，QWRT 25.12.2，Linux 5.4.213，约 1.75 GiB RAM。保持原调频、生产 DNS、IRQ 和网络配置。
- 独立网络命名空间；1 worker 限制 CPU1，2 workers 限制 CPU1–2；负载发生器 CPU0、固定上游 CPU3。每次只运行一个被测进程。
- 旧核心为 2026-09-12 07:34:24 UTC 的发布程序，DNS 源码与 `0bd6482` 相同；新核心从 `ef064b400a10045d98b4b3c25b6ef495fdbbdc79` 编译，时间为 14:24:49 UTC。
- 两者均为 Rust1.96.0、AArch64 musl、openwrt 功能、opt-level3、thin LTO，并使用既有编译训练数据。编译器报告已丢弃 IPSet 中间件和配置构建函数的过时控制流计数。本轮未重新训练，结论针对当前交付方式，不能拆分为纯算法或单独 PGO 的收益。
- 使用另一台 AP8220 原样复制的 CN 113,246 行和 GFW 28,380 行文件；未把名单复制进 Git 仓库。两种大名单配置使用相同的分组、TTL、AAAA 和响应策略，只有 IPSet 写入项不同。
- 工具来自现有 router_dnsbench.rs，仅将生成域名由 hostNNN.bench 改为 hostNNN.jd.com，使请求真实匹配完整国内名单。工具同时验证 DNS 问题区、成功状态和 192.0.2.1 答案。
- 缓存 4096 条、热域名 256 个、冷域名空间 100 万且计时期间不循环；关闭测速、双栈选择、预取、过期应答、持久化和审计。
- 等待监听器就绪，再等 1 秒并预热 1 秒。吞吐 5 秒、窗口 32；低负载延迟 10 秒、1000 QPS、窗口 4。新旧顺序在第二轮交换。模拟上游始终可用。
- 108 次测试共验证 18,546,262 个成功响应，零错误、零超时；冷回源数精确等于成功数减 255 个预热交集，热缓存与固定速率阶段回源均为零。每次 IPSet 场景还检查返回地址已在集合中。
- 修改前 IPSet 更新是后台任务，修改后等待内核确认后回复。因此该场景的时序语义不同：新版本修复客户端首个连接可能赶在分流规则之前的问题，不能以重新提前回复作为性能优化。
- 此固件未启用 nftables 集合支持，本轮实际测试 legacy IPSet。未用公网链路、加密上游或数天运行替代这些短时本地结果。
- 初次启动脚本发现固件 sleep 不接受小数，在产生测量数据之前退出；改为整数秒就绪轮询后重新开始。所有发布数据均来自修正后的完整批次。
