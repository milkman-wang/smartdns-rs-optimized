# 测速响应等待修复（2026-09-06）

## 问题与修复

开启 `speed-check-mode` 后，原先被跳过的 `fastest-ip` 路径开始工作。
旧实现只在第一次测速成功后，才给剩余上游增加 200 ms 等待限制。
遇到 NODATA、没有可测速地址或全部测速失败时，客户端可能等待慢上游的完整超时，实测约 5 秒。

现在 `fastest-ip` 和 `first-ping` 都在收到第一份有效 DNS 回答后，
给剩余上游一个固定的 200 ms 比较窗口；后续回答不会重置窗口。
这不是把查询总超时改成 200 ms：尚未收到有效回答时仍沿用上游超时，
已开始的测速也仍按各自的超时完成。窗口内稍晚到达的有效地址仍可参与选择。

同时修复 `first-ping` 中一组测速失败便提前退出的问题：
现在会继续处理其他未结束的查询和测速。无地址响应不再启动空测速任务。

## 路由器对照

- Xiaomi BE10000，沿用实际上游、域名规则与 2 个工作线程。
- 修复前后各运行独立测试实例，均为 `fastest-ip`、`ping,tcp:80,tcp:443`，双栈优选关闭。
- 两个实例均关闭缓存、持久化、预取和过期缓存返回，不修改生产缓存。
- 6 个域名分别查询 A/AAAA，共 12 次/版本，并发数 4。
- 原始结果见 [speed-check-20260906.json](speed-check-20260906.json)。

| 查询 | 修复前 | 修复后 |
| --- | ---: | ---: |
| www.bilibili.com AAAA（无地址） | 5006 ms | 223 ms |
| www.baidu.com AAAA | 5006 ms | 223 ms |
| www.qq.com A | 5004 ms | 613 ms |
| 全部查询中位数 | 291 ms | 221 ms |
| 全部查询最大值 | 5006 ms | 626 ms |

两组均无 DNS 错误。网络查询按修复前、修复后的顺序执行，并非严格同时的网络实验；
这些数字用于展示本次等待问题的消除，不代表所有网站的固定性能。
测速仍有成本，例如 B 站 A 查询在两组中均约 626 ms。

## 验证与部署

5 个新增回归测试在路由器通过，覆盖 NODATA、负回答错误、
NODATA 后到达有效地址、全部测速失败以及 `first-ping` 继续处理后续结果。
另有 7 个缓存测试、3 个上游选择测试、1 个无记录错误转换测试通过。
缓存持久化测试首次因测试工作目录缺少 `logs/` 失败，创建隔离测试目录后通过。

发布构建、格式检查及 Clippy（`-D warnings`）通过。修复版已部署到该路由器，恢复 `fastest-ip`，保留已关闭的双栈优选。
部署后 160 次 A/AAAA 查询无错误，平均约 39 ms、最大约 531 ms（含缓存，不与上表直接比较）。
UDP/TCP、本地主机名、HTTPS 记录及不存在域名的返回检查也通过。
