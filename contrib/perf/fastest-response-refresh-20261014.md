# fastest-response 测速写回缓存（2026-10-14）

## 改动

`response-mode fastest-response` 且配置了测速模式时，未命中缓存的查询仍直接返回最先到达的有效上游回答；同一次查询随后继续等待其他上游，对所有地址测速，用实测最快的地址替换缓存，之后的查询直接得到最快地址。
C SmartDNS 中 `response-mode` 只决定首次回复，请求结束时把测速后的最佳地址写入缓存；本改动与之对齐，测速也不会再查询一次上游。

- 只有一个地址的回答也会测速：其他上游可能返回不同且更近的地址。
- 客户端拿到回答后，不再只给其他上游 200 毫秒（这个窗口是为了不让慢上游拖住等待中的客户端），上游仍在递归的冷门域名也能参与比较；各上游仍受自身查询超时限制。
- 回复后先暂停，缓存决定保留时才开始测速；不缓存的回答（否定回答、`no-cache` 等）不会产生测速。
- 最多 128 个查询同时处于回复后继续测速的状态。超出时（例如大量不重复域名的洪泛）按原来的 `fastest-response` 回复，条目保持未测速，等预取或过期后再刷新。
- 每个缓存条目同时只运行一个测速，失败只释放条目，不推迟预取。测速后的回答会再做一次 bogus-nxdomain 检查；双栈优选只比较首次回复。`speed-check-mode none` 保持原来的行为。

本分支的第一版（5961829）在回复后由缓存再发起一次后台 `fastest-ip` 查询，即对所有上游再查一轮后测速。
选出的地址质量相同，但每次未命中都多一轮上游查询，并要排队等待后台查询共用的 16 个并发槽。下文的“第一版”即指它。

## 电脑上的对比（真实上游，日本网站）

Windows 11，经路由器 10G 有线连接；上游与路由器一致（2620:119:35::35、2001:4860:4860::8888、2606:4700:4700::1111）。
Windows 上 ICMP 需要管理员权限，测速模式用 `tcp:443,tcp:80`。
main（c855d46）、第一版和复用版三个实例同时运行，每个域名同时发给所有实例，5 秒后读取缓存回答，最后对出现过的每个地址做三次 TCP 443 握手取最小值。
“上游查询”数自各实例的 debug 日志，每次查询发往全部 3 个上游；超过 103 的部分是 TTL 很短的记录（如 Akamai 的 20 秒）过期后由 serve-expired 触发的后台刷新，三个版本相同。

只测 103 个日本网站：中国网站的国际线路普遍劣化，CDN 又每次返回不同城市的地址
（例如 www.speedtest.cn 的三个上游每次都给出不同的单个地址，往返约 200 毫秒），选择结果主要取决于运气。

| 1 | 复用版 | 7.4 | 13.8 | 21.4 | 8.7 | 127 | 0.2 | 99% |

| 2 | 第一版 | 7.4 | 14.7 | 22.3 | 8.6 | 218 | 0.2 | 100% |

## 路由器洪泛（开启测速）

小米 BE10000，QWRT 25.12.2 R26.10.7、Linux 5.4.213。
`run_router_flood.sh`（`PERF_VARIANTS="old prev new"`，第二轮倒序）：`fastest-response` 加 `ping,tcp:443,tcp:80`，双核，100 万个不重复域名满速查询 20 秒。
固定上游总是回答 192.0.2.1，命名空间内把该网段路由到 dummy 接口，每次测速都等到超时，相当于目标不可达。

- old：main c855d46；prev：第一版 5961829；new：本改动。三者使用同一工具链（Rust 1.99.0、zig 0.17.0）和相同编译选项。

| 版本 / 轮次 | 次/秒 | P99（微秒） | 结束时 RSS | 额外上游查询 |
|---|---:|---:|---:|---:|
| old / 1 | 44,053 | 1,258 | 15.0 MiB | 0 |
| prev / 1 | 42,509 | 1,298 | 15.4 MiB | 544，停止后 +112 |
| new / 1 | 42,693 | 1,317 | 16.6 MiB | 0 |
| new / 2 | 42,908 | 1,314 | 16.6 MiB | 0 |
| prev / 2 | 40,299 | 1,733 | 15.7 MiB | 544，停止后 +112 |
| old / 2 | 43,907 | 1,229 | 15.0 MiB | 0 |

停止 10 秒后 RSS 基本不变（prev 第一轮从 15.4 增至 15.7 MiB）。第一版的刷新排队等待后台查询的 16 个并发槽，20 秒内只完成 544 次，每次都再查询一轮上游；
new 不再查询上游，最多 128 个同时测速，每次测速都等满 3 × 200 毫秒，按此推算每秒约 210 个查询拿到名额，其余按原方式回复。
new 的吞吐与第一版相当，比 main 低约 3%。

## 复现

```sh
# 电脑：分别运行各版本的 SmartDNS 实例后
dns_quality_bench domains.txt out.tsv main=127.0.0.1:15311 prev=127.0.0.1:15312 reuse=127.0.0.1:15313

# 路由器：洪泛与吞吐（需在专用网络命名空间内，目录中放 ./smartdns-<版本> 与 ./dnsbench）
ip netns exec smartdns-flood env PERF_NETNS=smartdns-flood PERF_DIR=/tmp/smartdns-flood \
    PERF_VARIANTS="old prev new" sh run_router_flood.sh
ip netns exec smartdns-flood env PERF_NETNS=smartdns-flood PERF_DIR=/tmp/smartdns-flood \
    RESULTS=/tmp/smartdns-flood/qps-results.jsonl VARIANTS="old-w1 new-w1 old-w2 new-w2" ROUNDS=3 \
    sh run_release_comparison.sh
```

R26.10.7 自带的 `ip`（iproute2 5.0.0）执行 `ip netns add` 后会段错误，但命名空间已经创建并挂载，`ip netns exec` 与 `ip netns del` 可以正常使用；新命名空间需先 `ip link set lo up`。
