# 小米 BE10000 / QWRT 实测，2026-09-06

## 环境和方法

- Xiaomi Router BE10000 (Wi-Fi 7)，QWRT 25.12.2 / R26.8.8 (QSDK 12.5)，Linux 5.4.213，`ipq95xx/generic`。
- 四核 AArch64，CPU implementer `0x41`、CPU part `0xd09`；软件包架构标识 `aarch64_cortex-a53`。
- 保持 `ondemand` governor，未修改频率；可用频点 936–2208 MHz。
- Rust 1.96.0，`aarch64-unknown-linux-musl`，使用 Rust 自带 musl/lld 最终链接。启用与 OpenWrt 包相同的协议/nft/serde 功能集合。产物为直接交叉编译的静态二进制，并非 SDK IPK。
- 代码基于 `f6a382c`。基线为原路由器的 0.13.1 二进制，**已经包含“有效缓存命中不再启动后台查询”的修复**。不能把那项既有修复的收益再次算成本轮收益。
- 两者均保留 LTO、单 codegen unit 和符号剥离。最终版改为 `opt-level=3`，完成缓存插入后才返回，重置预取标记，并把预取限制为同时 16 个域名、每秒最多启动一批。

最终吞吐测试在路由器的独立网络命名空间内进行，不经过生产网络。固定上游监听 127.0.0.1:5301，返回 `192.0.2.1`、TTL 3600；测试服务监听 5300。客户端和固定上游使用 CPU 0，服务使用 CPU 1–3，正式 DNS 服务继续运行。

热缓存使用 256 个域名，缓存容量 4096；每次启动后先以并发 1 预热 1 秒，再以并发 32 测量 5 秒。每组 5 轮，穿插基线、优化版 4 线程和优化版 2 线程。指标报告逐轮中位数，百分位数没有跨轮合并。

| 相对基线 | — | +55.5% | +97.9% |
| P95 | 1.963 ms | 1.200 ms | 0.911 ms |
| P99 | 2.527 ms | 1.709 ms | 1.052 ms |
| 服务 CPU，100%=一个核心 | 150.6% | 147.2% | 179.2% |
| 小配置服务 RSS | 5,604 KiB | 7,116 KiB | 7,044 KiB |
| 错误、超时 | 0 | 0 | 0 |

逐轮原始数据见 [router-20260906.json](router-20260906.json)。CPU 数字来自饱和负载，2 线程版本处理了更多查询，因此不能把 CPU 百分比直接当作每次查询的成本。

前期使用全部 CPU 核心运行服务、客户端仍在 CPU 0 的 3 轮验证，也测得 2 线程优于 4 线程，分别约 50,918 和 42,127 QPS。这支持本机选择 2 线程，没有修改其他机器的默认值。

## 冷缓存结果

在同一独立网络命名空间中，每轮使用 65,536 个域名，远大于 4,096 条缓存容量，除最初少量预热条目外查询均需上游。每组 3 轮，轮间只清理测试命名空间中 127.0.0.1:5301 的 UDP 连接。

冷缓存数据来自加入每秒预取节奏控制之前的并发限制版；本基准关闭预取，前台查询路径与最终版相同。上面的热缓存数据则使用最终部署产物重新完成了全部五轮。

| 指标，中位数 | 基线，4 线程 | 优化版，4 线程 | 优化版，2 线程 |
|---|---:|---:|---:|
| QPS | 11,188.9 | 11,607.8 | 15,631.7 |
| 相对基线 | — | +3.7% | +39.7% |
| P99 | 6.343 ms | 4.871 ms | 3.108 ms |
| 服务 CPU，100%=一个核心 | 241.9% | 166.3% | 185.3% |
| 错误、超时 | 0 | 0 | 0 |

4 线程下冷缓存吞吐提升有限，CPU 开销下降；2 线程在本机两类负载下均更合适。固定上游没有公网 RTT，因此这些数字不能预测公网冷查询的延迟提升。

## 测试中发现并处理的问题

早期在宿主网络进行的冷缓存极限压测填满了 65,535 条连接跟踪表，两个版本都出现丢包。内核明确报告 `nf_conntrack: table full, dropping packet`。这批冷缓存结果不用于性能结论。测试停止后连接自然过期，宿主连接数恢复；没有清空用户连接或调整防火墙/连接跟踪上限。后续测试改用独立网络命名空间。

第一版速度优化产物在完整配置下还暴露了批量预取内存问题：8,000 条持久化缓存加载后，RSS 曾达到约 273 MiB，VmHWM 约 295 MiB。立即恢复了原二进制和配置，没有把功能查询通过当作部署成功。

原因是预取为整批过期域名创建任务，应用层的并发上限按“批次”而不是按“请求”计数。只限制同时进行的请求仍不够：后续线上观察中，快速连续刷新占满两个核心，本地域名延迟达到数百毫秒，因此再次恢复了原版。

最终预取最多同时处理 16 个域名，每秒最多启动一批，慢批次不补发积压的时钟 tick。其余域名排队，成功更新会清除预取标记。这样保留预取功能，同时给前台请求和连接跟踪表留出余量。8,000 个域名的整批刷新至少需要约 500 秒；排队期间仍可正常按需解析和返回过期缓存。

## 内存和功能验证

- 并发限制版：8,000 条同时过期的合成缓存、TTL 0 的固定上游，峰值 RSS 19,120 KiB，随后 15,532–16,872 KiB。该测试专门触发集中预取；测试缓存文件曾因 root 所有权导致退出写入失败，改为服务用户所有后完成。
- 并发限制版：完整 37,648 条屏蔽规则和 8,000 条真实缓存的独立实例，160 次 A/AAAA 加 UDP/TCP、HTTPS/NODATA/NXDOMAIN 和本地域名检查通过。观察期间 RSS 30,396–30,588 KiB；包括启动规则加载在内的 VmHWM 66,172 KiB。这些功能和内存检查没有发现随后部署时暴露的 CPU 问题，因此最终版增加了主动预取负载下的延迟和 CPU 检查。
- 对最终节奏控制版主动注入 TTL 0 的专用测试域名，触发真实缓存预取：本地域名约 0.4–1.3 ms，RSS 29,532–29,908 KiB。30 秒内服务 CPU 约为一个核心的 39%–66%，而此前无节奏控制时持续约 199%。这是集中刷新时的开销，不是空闲功耗。专用上游和域名规则只存在于测试实例。
- 在路由器执行 7 个缓存单元测试，覆盖有效命中、过期刷新、预取重新调度、并发上限和队列排空、持久化、CNAME 顺序；另有 3 个多上游负响应测试和 1 个无 SOA 的 NODATA 响应测试，全部通过。
- 新旧静态二进制约为 9.3 MB 和 6.3 MB。隔离小配置的 RSS 不代表完整配置的内存。

## 最终部署

最终节奏控制版已替换路由器 `/usr/sbin/smartdns`，实际大小 9,244,216 字节，并与被测产物逐字节比较一致。自定义配置仅追加 `num-workers 2`，保留原规则、上游、8,000 条持久化缓存和预取设置。

部署后 160 次并发 A/AAAA 查询零错误，另有 12 次 UDP/TCP 功能检查通过。本地域名 UDP 为 0.38–1.18 ms，混合公网 A/AAAA 查询平均 38.27 ms、最大 311.89 ms；这些公网数值只用于功能健康检查。30 秒内 RSS 为 29,452–29,756 KiB，后续为 30,116 KiB；启动 VmHWM 为 66,208 KiB。六个 5 秒窗口的 CPU 为单核的 35%、22%、27%、32%、36%、59%，仍包含启动后的缓存刷新工作，不能视为空闲 CPU。IPv4/IPv6 的 UDP/TCP 53 端口均正常监听，测试实例、固定上游和测试网络命名空间已停止并清理。

原二进制、原自定义配置和原生成配置保存在路由器 `/root/codex-backups/20260906-smartdns-performance/`，没有覆盖。需要恢复时：

```sh
B=/root/codex-backups/20260906-smartdns-performance
cp "$B/smartdns.before" /usr/sbin/smartdns.restore
chmod 755 /usr/sbin/smartdns.restore
/etc/init.d/smartdns stop >/dev/null 2>&1
sleep 2
# 确认 pidof smartdns 无输出后再执行以下替换。
mv /usr/sbin/smartdns.restore /usr/sbin/smartdns
cp "$B/custom.conf.before" /etc/smartdns/custom.conf
/etc/init.d/smartdns start
```

本次执行了上述 11 个相关单元测试、Rust 格式检查和基准 C/脚本检查；没有运行整个仓库的全部测试或完整 OpenWrt SDK 打包。

## 复现

[router_dnsbench.rs](router_dnsbench.rs) 现为 Rust 实现，交叉编译后路由器不需要 Python 或 Rust 工具链。历史结果使用当时的 C 工具；后续比较应统一使用同一版基准工具。它仅生成本基准的普通 A 查询，没有 EDNS/DNSSEC；上游模式只用于这组查询。吞吐测试请放在独立网络命名空间，避免冷缓存流量占用生产连接跟踪表。

```sh
# 在安装 Rust 目标工具链的交叉编译主机上。
cargo build --manifest-path contrib/perf/Cargo.toml --locked --release --target aarch64-unknown-linux-musl
cp contrib/perf/target/aarch64-unknown-linux-musl/release/router_dnsbench dnsbench

# 将 dnsbench、run_router_bench.sh 和待测二进制上传到路由器。
mkdir -p /tmp/smartdns-perf
chmod +x /tmp/smartdns-perf/dnsbench
ip netns add smartdns-perf
ip netns exec smartdns-perf ip link set lo up
ip netns exec smartdns-perf taskset 1 /tmp/smartdns-perf/dnsbench server 5301 &
upstream_pid=$!

ip netns exec smartdns-perf sh /tmp/smartdns-perf/run_router_bench.sh \
  /path/to/baseline 4 cache baseline
ip netns exec smartdns-perf sh /tmp/smartdns-perf/run_router_bench.sh \
  /path/to/optimized 4 cache optimized
ip netns exec smartdns-perf sh /tmp/smartdns-perf/run_router_bench.sh \
  /path/to/optimized 2 cache optimized-w2

kill "$upstream_pid"
ip netns delete smartdns-perf
```

`PERF_DIR` 指定测试目录，`SERVER_CPU_MASK=f` 让服务使用全部四个核心。`static` 场景使用 address 规则，`cold` 使用 65,536 个域名超过缓存容量。每轮冷缓存测试后可在**测试命名空间内**删除目标 127.0.0.1:5301 的测试 UDP 连接，避免跨轮积累。

## 结果边界

这是闭环饱和负载，客户端也在路由器上运行，用于比较同机改动的相对收益，不能当成外部有线客户端可达到的绝对容量。CPU 频率、正式 DNS 和其他路由工作可能引入波动，因此保留全部样本。

未测试 C SmartDNS 对照，也未把公网 UDP/DoH/DoT 等待时间算作编译优化收益。这里的 QPS 提升比例不能套到网页加载速度。2 线程是本机实测选择，Rust 的跨平台默认线程数没有改变。
