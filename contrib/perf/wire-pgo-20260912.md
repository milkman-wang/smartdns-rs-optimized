# 编码复用、PGO 与实体 LAN 对照（2026-09-12）

本轮在 [上一轮 TTL 复用最终版](router-efficiency-20260912.md) 基础上继续优化。选用通用 AArch64 的编码复用 + PGO 构建；未采用 Cortex-A73 专用目标，也没有更改路由器的全局网络或调频配置。

**发布候选安装包使用 PGO。普通 `cargo build --release` 只获得本轮编码复用的代码收益，不会自动获得表中的全部 PGO 收益。** 下文给出分项对照和构建流程。

## 相对上一轮最终版

同批 96 次测试：两版 × headless/WebUI × 1/2 workers × 冷/热/100 QPS/1000 QPS × 3 轮。各列为三轮中位数，P99 是每轮 P99 的中位数，不是合并所有请求后的分位数。[原始数据](wire-pgo-20260912.json) 保留逐轮值和范围。

设备 BE10000，QWRT 25.12.2，Linux 5.4.213，AArch64；governor 保持 ondemand。单 worker 绑定 CPU1，双 worker 绑定 CPU1–2；客户端 CPU0，模拟上游 CPU3。每轮启动、预热各 1 秒；吞吐 5 秒、32 在途请求；固定速率各 10 秒、4 在途请求。

缓存 4096 条，热集 256 域名；冷测试为 100 万域名空间，期间不循环。上游为固定 A 记录、TTL 3600，关闭测速、预取、过期应答、双栈择优和审计。每次冷测试上游计数精确等于成功数减 255（预热交集），热吞吐暂停上游且上游计数为零；96 次均零错误、零超时。

## PGO 独立收益与 CPU 专用编译

普通编码复用版（compact）与同源 PGO 版另做 48 次同批三轮冷热对照：

| headless / 2 | 43,283 → 53,127 | +22.7% | 114,016 → 114,167 | +0.1% |

双 worker headless 热吞吐在这个批次基本持平，尽管 CPU 成本下降。后面的独立发生器对照表明，单一发生路径会掩盖最终版的容量；不能仅据此表判断服务器已没有双核收益。单核改善有助于多核，但并不保证所有指标线性扩展。

Cortex-A73 专用编译相对普通编码复用版另做单轮 16 次冷热筛选：冷查询小幅正负波动，热查询没有一致提升，WebUI 热查询略低。没有证据支持为此限制发布包的硬件适用范围。此单轮筛选不证明 CPU 特化在所有负载都无效。

## 发生器容量对照

为检查约 11.4 万 QPS 的平台期，另做 12 次三轮对照：DNS 服务仍固定 CPU1–2；单发生器在 CPU0，32 个在途请求；双发生器在 CPU0、CPU3，各 16 个在途请求，总数仍为 32。热测试暂停上游，所以 CPU3 可用于第二个发生器。两个客户端的 QPS 相加，同一服务进程的 CPU 指标不重复累加，也不把两个 P99 平均成全局 P99。

| 发生器数 | 上一轮版 QPS | 最终版 QPS | 提升 |
|---|---:|---:|---:|
| 1 | 105,944 | 114,638 | +8.2% |

## 功能、交付与范围

最终源代码 351 项测试通过、0 失败、1 忽略；Windows 全目标 Clippy 和 AArch64 musl Clippy 通过。新增测试验证编码随 TTL、记录及 EDNS 修改失效；共享回复测试覆盖请求头、section 数、EDNS 和扩展响应码。普通构建与 PGO 采用相同源代码。

最终路由器产物在 headless/WebUI、1/2 workers 四组通过 IPv4/IPv6 UDP、TCP、域名/监听/客户端 ipset，以及停上游后的缓存命中与 ipset 恢复检查。单 worker WebUI 与 1000 QPS 同时运行 15 秒，15,000 次查询全部成功，最终活动查询为 0、历史 1000 条、缓存 256 条。两个 IPK 的可执行载荷逐字节等于实测最终二进制，权限 0755。

本轮不改变上游解析策略或全局 CPU/NIC 设置，也没有将真实公网冷查询伪装成缓存命中。只在这一台 ARM 路由器上测性能；其他 SoC、更多客户端、不同 DNS 记录和加密协议负载仍需对应验证。

默认调度下 LAN P99 的三轮中位数改善约 4%–11%。绑核在 1000 QPS 下进一步降低部分尾延迟，在 100 QPS 下略有退步，因此保持原有调度配置，不把某个固定 CPU 掩码作为通用优化。

## 本轮优化边界

代码只保留受预算约束的编码复用：同一剩余 TTL 下的热门响应保留现有协议库产生的字节；发送时继续按请求改写头部，保留编码器计算的 section 数量和截断标志。TTL、记录、EDNS 或响应码改变时失效。没有自写 DNS 解析器、额外缓冲池或硬件专用运行分支。

初版把整个 DnsResponse 搬进传输枚举，热查询提高但冷查询退步约 3%–4%。最终传输枚举只携带共享报文、可选编码、响应头和地址，撤回了多余的数据传递。复用编码减少了重复压缩、编码器准备和记录遍历，仍为每个发送报文生成可独立修改的字节；它不是零拷贝或内核旁路。

## PGO 与编译复现

PGO 根据实测分支和调用频率指导编译器的内联、代码布局等优化，不增加运行时采集器或依赖，也不等于启用了额外 CPU 指令。依据：[Rust PGO 文档](https://doc.rust-lang.org/rustc/profile-guided-optimization.html)。本轮 CPU 专用编译单独比较，未把两种收益混在一起。

工具链：Rust 1.96.0 / LLVM 22.1.2，AArch64 musl，opt-level=3、codegen-units=1、thin LTO；两个变体分别启用 openwrt 和 openwrt,webui。训练与最终构建使用相同源代码和功能组合。21 份有效 profile 覆盖冷热 UDP、100/1000 QPS、IPv4/IPv6 UDP/TCP、域名/监听/客户端 ipset 和 WebUI 快照。该训练不代表公网加密上游性能。

基本流程（路径替换为实际绝对路径，跨编译还需设置对应 CC/AR/linker）：

```sh
# 采集构建，headless 和 webui 分别运行一次
CARGO_TARGET_DIR=target/pgo-generate CARGO_PROFILE_RELEASE_LTO=thin \
RUSTFLAGS='-C profile-generate=/absolute/profile-dir' \
cargo build --release --no-default-features --features openwrt --target aarch64-unknown-linux-musl

# 将采集二进制放到测试设备，使用可由降权用户写入的临时目录
LLVM_PROFILE_FILE='/absolute/profile-dir/%m-%p.profraw' ./smartdns run -d /test-dir -c /test-dir/test.conf
# 运行代表性负载，正常退出并等待所有进程结束后收集数据
llvm-profdata merge -o /absolute/merged.profdata /absolute/profile-dir/*.profraw

CARGO_TARGET_DIR=target/pgo-use CARGO_PROFILE_RELEASE_LTO=thin \
RUSTFLAGS='-C profile-use=/absolute/merged.profdata' \
cargo build --release --no-default-features --features openwrt --target aarch64-unknown-linux-musl
```

本机额外使用 `-C link-self-contained=no` 配合已有 Zig 链接器。构建辅助脚本将其不接受的 `-u __llvm_profile_runtime` 转为 linker 参数形式。Rust 随附的 Windows profile 读取工具未启用 zlib，因此使用缓存目录中的 [MSYS2 LLVM tools 22.1.8](https://packages.msys2.org/packages/mingw-w64-x86_64-llvm-tools) 合并数据；没有替换系统工具链。最后使用 `profile-use` 构建，交付物不包含采集 instrumentation。后续源码、编译器或负载明显改变时，应重新训练并比较，不能把本次 profile 当作永久通用最优配置。

## 硬件与 LAN

实测设备 CPU part 为 0xd09，对应 Cortex-A73；包名中的 cortex-a53 是软件包架构标识。设备支持 NEON、AES、PMULL；现有 ring 0.17.14 根据 HWCAP 自动选择 ARM 加密指令路径。[CPU 标识](https://github.com/torvalds/linux/blob/master/arch/arm64/include/asm/cputype.h)。

实体网卡具有 4 个 RX/TX 队列；校验和卸载已开启，EDMA 收发中断已分布到 CPU0–3。没有修改 IRQ、RPS、XPS、硬件卸载或 ondemand 调频配置。NAT/流转发卸载不会替本地 DNS 应用执行规则和缓存查找；它解决的是不同路径的开销。[流转发说明](https://docs.kernel.org/networking/nf_flowtable.html)。

LAN 测试使用 Windows 电脑的 Realtek 10GbE 有线连接，固定客户端地址和 UDP 端口，保持 RSS 流哈希稳定；Wi-Fi 未连接。对照只调整临时 DNS 进程的 CPU 亲和性：默认允许 CPU0–3，单 worker 固定 CPU1，双 worker 固定 CPU1–2。每组 3 轮、100/1000 QPS 各 10 秒、最多 4 个在途请求，轮换顺序，报告实际达到的速率。Windows 临时请求 1 ms 定时器精度，结束后恢复。

此结果包含 Windows 客户端、网卡、LAN 和路由器调度，不能直接与 loopback 微基准相除，也不代表多客户端、多 UDP 流的 IRQ 最优配置。RSS/RPS/IRQ 与应用的局部性存在取舍，绑核不会普遍提高性能。[Linux 网络扩展说明](https://docs.kernel.org/networking/scaling.html)。

测量源文件：[冷/热隔离运行器](run_router_efficiency.sh)、[Linux DNS 负载工具](router_dnsbench.rs)、[Windows LAN 延迟客户端](lan_dnsbench.py)、[Linux PMU 计数工具](router_perfstat.c)。LAN 客户端使用本次固定的服务器/客户端地址和端口，复现到另一网络时需修改这两个地址；调用 `python lan_dnsbench.py 1000 10` 测 10 秒的目标 1000 QPS。PMU 工具以 `perfstat PID SECONDS` 运行，需要相应 perf 权限；它统计开始时已有的线程，不是调用栈火焰图。查询功能仍由基准客户端逐条验证。
